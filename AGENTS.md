# AGENTS.md

This file provides guidance to AI agents when working with code in this repository.

## Commands

```bash
bun dev            # The website (site/) in Vite, at localhost:4193
bun run test       # Run all tests (with the fieldspec@dev condition: source, not dist)
bun typecheck      # Type check (TypeScript 7, native tsc)
bun run lint       # Lint
bun run format     # Format
bun run fix        # Lint + format + autofix
bun run checks     # Everything: check + typecheck + test
bun run build      # dist/ with tsdown
bun run schema     # Regenerate schema/spec.json (CI runs `bun run schema --check`)
bun run check:package  # publint + are-the-types-wrong on the packed package
bun run demo       # The demo app (demo/) at localhost:4192
bun run stress     # Long randomized stress run over generated specs
```

Prefer these scripts over ad-hoc commands. Do not prefix them with `bun run` when
a bare alias exists (`bun check`, `bun typecheck`) — those are whitelisted for
agent use. Before finishing, run `bun run fix` then `bun run checks` — the linter,
formatter and `tsc` own all mechanical style rules. Fix the code; don't disable rules.

## Project Structure

One package, `fieldspec`, ESM-only, with five entry points (see `exports` in `package.json`).
Parent-directory imports go through the `#*` alias (`#src/form.ts`), siblings use `./`.

- `src/types.ts` — the serialized format: specs, field declarations, expressions. Plain JSON.
- `src/kinds.ts` — kinds (what `type` names): checks, JSON encoding, JSON Schema, default control.
- `src/elements.ts` — the element catalog `render` may name: layout, parts and controls.
- `src/presets.ts`, `src/defs.ts` — presets and definitions, and following `use` to them.
- `src/registry.ts` — a registry: the kinds, elements, presets and languages specs are written in; `define`.
- `src/infer.ts` — `Infer<typeof spec>`, the value type, at the type level only.
- `src/expr.ts` — conditions and expressions over form state; `$computed` functions; the `Language` interface.
- `src/cel.ts` — `fieldspec/cel`: the language that runs `$cel` (`@marcbachmann/cel-js`), the recommended one.
- `src/js.ts` — `fieldspec/js`: the language that runs `$js`, sandboxed in QuickJS (`@gkurt/quickjs-wasi`).
- `src/values.ts` — values against a spec: decode, encode, defaults, `parse`, `validate`.
- `src/check.ts` — `checkSpec`: every fault at a JSON Pointer, phrased as the fix.
- `src/layout.ts` — a spec's fields, groups and `render`s resolved into one `LayoutNode` tree.
- `src/form.ts` — `createForm`, the headless form: values, field state, issues, layout.
- `src/common.ts` — `commonFields`: one spec for the fields several specs share, with mixed values.
- `src/locales.ts` — translations: `texts`, `localize`, `checkTranslations`, over a spec's `locales`.
- `src/patch.ts`, `src/pointer.ts` — JSON Patch over values; JSON Pointers.
- `src/jsonschema.ts`, `src/zod.ts`, `src/standard.ts`, `src/jsonrender.ts` — interop.
- `src/prompt.ts`, `src/schema.ts` — a system prompt and the JSON Schema of specs, for agents.
- `src/version.ts` — `VERSION`, written by the Tegami config on each release (see below).
- `src/react/index.tsx` — `fieldspec/react`: `FormView`, the renderer protocol, text parsing. No look of its own.
- `src/react/controls.tsx` — what container and choice controls do: `listOf`, `entriesOf`, `variantOf`, `objectOf`, `choicesOf`, `checksOf`.
- `test/` — `bun test` suites; `test/stress/` generates random specs and checks invariants.
- `site/` — the website (Vite, React), deployed to GitHub Pages by `pages.yml`.
- `examples/renderers/` — renderer sets to copy (HTML, DialKit, React Aria), not shipped; they import fieldspec by its package name, which the `fieldspec@dev` condition resolves to source.
- `examples/design.ts` — a custom registry used by tests and the demo; `demo/` — a design-tool demo app.
- `experiments/` — studies with small models (spec generation, filling); their `out/` is data.
- `schema/spec.json` — the generated JSON Schema of specs, shipped and served by unpkg.
- `SKILL.md` — a skill for agents in projects that use fieldspec, shipped in the package.
- `site/public/llms.txt` — the site's llms.txt: what fieldspec is and where its docs are.

## Architecture

- **A spec is data.** Everything in `src/types.ts` is JSON: specs can be stored, sent and
  generated by agents. Conditions are expressions, not functions; code reaches in only through
  named `$computed` functions supplied at runtime, or as `$cel` or `$js` source the spec carries,
  run by a registry's language. Code reads only its `args`, so what it depends on stays visible.
  Keep the expression grammar json-render's: what it cannot say belongs in `$cel` (or `$js`),
  not in new keys. CEL is the one to recommend; QuickJS is heavy, for what CEL cannot say.
- **A registry is the vocabulary.** Kinds, elements and presets live in a `Registry`; the core
  registry is the default and `createRegistry` extends it. The checker, JSON Schema, prompt and
  layout all read the registry, so a custom kind or element works everywhere at once.
- **Headless first.** `createForm` holds values and computes each field's state and a
  `LayoutNode` tree; it knows nothing of React. `fieldspec/react` walks that tree and asks
  renderers (a table keyed by element name, or a function) to draw each node. Renderers get
  props by role: `LayoutProps`, `PartProps`, `FieldProps`, `ControlProps`. fieldspec ships no
  look: behaviour lives in `src/react/controls.tsx`, visuals in `examples/renderers/`.
- **Names**: built-in names are lowercase, user-defined ones capitalized.
- **Versioning**: `VERSION` in `src/version.ts` and the `$id` of `schema/spec.json` carry the
  package version. Don't edit them by hand: a Tegami changelog entry bumps the version, and
  `scripts/tegami.mts` rewrites both in the version PR.

## Coding Conventions

- Prefer colocation.
- Avoid verbose code comments; write self-explanatory code. Comments are acceptable for:
  - Explaining complex logic, workarounds, or decisions
  - Documenting public APIs (functions, classes, modules)
  - TODO/FIXME notes
  - When the user specifically asks for comments
- Prefer early returns and guard clauses over nested conditionals.
- Check for existing utilities/hooks/components before creating new ones. Avoid duplication.
- Remove dead and commented-out code; don't preserve old APIs unless asked.
- Line endings are LF, on every OS. Scripts that write files must write LF too: on Windows, Python's text mode writes CRLF unless opened with `newline=''`.
- When moving or relocating code (functions, components, utilities), don't leave a re-export behind for backwards compatibility. Update every importer to point at the new location and delete the old definition, so there is a single source of truth.

## Documentation

When changing user-facing APIs, update all relevant docs in the same change:
docs pages (`site/`), README.md, SKILL.md, AGENTS.md, `site/public/llms.txt`. Documentation must not go stale.
Every change that ships needs a Tegami changelog entry (`.tegami/<slug>.md`; see the
`changelog` skill).
